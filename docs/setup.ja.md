# セットアップ

[English](setup.md) | 日本語

シェルへの連携は `runex init` が行います。このページでは、`runex init` が書くファイル、決して触らないもの、シェルごとの注意点、`runex doctor` での確認方法を説明します。

## `runex init` を実行する

`runex init` は設定ファイルを作成し、シェル連携のキャッシュファイルを書き、rc ファイルの末尾に `source` 行を 1 行追記します。書き込みのたびに確認を求めます。

```
$ runex init
Create config at ~/.config/runex/config.toml? [y/N] y
Created: ~/.config/runex/config.toml
Install shell integration (cache at ~/.cache/runex/integration.bash, source line in ~/.bashrc)? [y/N] y
Wrote integration cache to ~/.cache/runex/integration.bash
Appended source line to ~/.bashrc

Next steps:
  1. Reload your shell: `source ~/.bashrc` (or `exec $SHELL`)
  2. Try `gst<Space>` — it should expand to `git status `.
  3. Add your own abbreviations: see https://github.com/ShortArrow/runex/blob/main/docs/recipes.md
  4. Verify any time with: `runex doctor`
```

シェル名を省略すると、`$SHELL`（Windows では `$PSModulePath`）からシェルを判定します。`runex init <shell>` で `bash`、`zsh`、`pwsh`、`clink`、`nu` のいずれかを直接指定できます。`-y` を付けると、すべての確認に yes と答えます。

実行後は新しいシェルを開いてください。rc ファイルはシェル起動時に読まれるので、実行したセッションには反映されません。

## `runex init` が書くファイル

シェルごとに 2 つのファイルを書きます。どちらも `runex init <shell>` を再実行するたびに書き直されます。

**キャッシュファイル**には、シェル関数とキー束縛が入ります。置き場所は `XDG_CACHE_HOME` に従います。この環境変数が無いときは、Linux と macOS では `~/.cache`、Windows では `%LOCALAPPDATA%` を使います。

| シェル | Linux / macOS | Windows |
|---|---|---|
| bash | `~/.cache/runex/integration.bash` | `%LOCALAPPDATA%\runex\integration.bash` |
| zsh | `~/.cache/runex/integration.zsh` | `%LOCALAPPDATA%\runex\integration.zsh` |
| pwsh | `~/.cache/runex/integration.ps1` | `%LOCALAPPDATA%\runex\integration.ps1` |
| nu | `~/.cache/runex/integration.nu` | `%LOCALAPPDATA%\runex\integration.nu` |
| clink | `~/.local/share/clink/runex.lua` | `%LOCALAPPDATA%\clink\runex.lua` |

clink の置き場所は環境変数 `RUNEX_CLINK_LUA_PATH` で変更できます。

キャッシュファイルの先頭には 3 行のヘッダーがあります。

```bash
# runex-integration-version: 2
# runex-bin: /home/me/.cargo/bin/runex
# Generated by `runex init bash`; do not edit.
```

`runex-bin:` の行には、`runex init` を実行したバイナリの絶対パスが入ります。キー押下ごとのフックはこのパスを直接呼ぶので、`PATH` の検索も、バージョン管理ツールの shim も、1 打ごとには動きません。`runex doctor` はこのヘッダーと実行中のバイナリを突き合わせ、古いキャッシュを報告します。

**rc ファイルの行**は、`# runex-init` のマーカーを付けた 1 ブロックとしてファイル末尾に追記されます。

| シェル | rc ファイル | 追記される行 |
|---|---|---|
| bash | `~/.bashrc` | `[ -r '<cache>' ] && . '<cache>'` |
| zsh | `~/.zshrc` | `[ -r '<cache>' ] && . '<cache>'` |
| pwsh | Windows では `~/Documents/PowerShell/Microsoft.PowerShell_profile.ps1`、それ以外では `~/.config/powershell/Microsoft.PowerShell_profile.ps1` | `if (Test-Path '<cache>') { . '<cache>' }` |
| nu | `$XDG_CONFIG_HOME/nushell/env.nu`、無ければ `~/.config/nushell/env.nu` | `if ('<cache>' | path exists) { source '<cache>' }` |
| clink | なし。clink はスクリプトディレクトリ内の `.lua` をすべて読み込む | なし |

## キャッシュが再生成されるタイミング

キャッシュファイルに埋め込まれるのは `[keybind]` の設定だけです。`[[abbr]]` のルールは埋め込まれません。フックはキー押下のたびに `config.toml` を読むので、追加したルールは次のキー押下から効きます。

| 契機 | キャッシュへの影響 |
|---|---|
| `runex init <shell>` | キャッシュを書き直し、rc ファイルの行も確認する |
| `runex add`、`runex remove` | 既に存在するキャッシュをすべて書き直す。書き直しに失敗しても警告を出すだけで、終了コードは変わらない |
| `runex config reload` | 既に存在するキャッシュを、現在の設定ファイルからすべて書き直す。`config.toml` を手で編集したあとに実行し、新しいシェルを開く |
| `runex doctor` | 古いキャッシュを報告する。書き換えはしない |

`runex config reload` はシェルごとに 1 行ずつ結果を表示します。

```
$ runex config reload
bash: refreshed /home/me/.cache/runex/integration.bash
zsh: not installed (run `runex init zsh` to create its cache)
```

設定ファイルが読み込めないときは終了コード 1 で止まり、キャッシュには何も書きません。clink の lua ファイルはこのキャッシュには含まれず、`runex init clink` だけが書き直します。

## `runex init` が決してしないこと

- 既存の設定ファイルを上書きしない。`create_new` で作成するので、既にあるファイルはそのまま残り、その旨を表示する。
- あなたが書いた行を変更しない。rc ファイルは追記モードで開き、ブロックは最終バイトの後ろに置く。
- rc ファイルのパスにあるシンボリックリンクを辿らない。Unix では `O_NOFOLLOW` で開く。
- 二重に追記しない。`# runex-init` のマーカーが既にあれば、rc ファイルには触れない。
- 1 MB を超える rc ファイルには追記しない。そのようなファイルはマーカーが無いものとして扱い、追記を拒否する。
- 書きかけのキャッシュを残さない。隣に一時ファイルを書いて同期し、名前を変えて置き換える。

これらの保証は `runex/tests/cli_integration.rs` のテストで固定しています。

**アンインストール**は、rc ファイルの `# runex-init` から次の空行までを削除し、キャッシュファイルを削除します。設定も不要なら `~/.config/runex/config.toml` を削除してください。

## dotfiles を自分で管理している場合

`runex export <shell>` は、`runex init` がキャッシュファイルに書く内容をヘッダーごと出力します。rc ファイルを別のツールで生成している場合や、複数マシンで同期している場合に使ってください。

```bash
mkdir -p ~/.cache/runex
runex export bash > ~/.cache/runex/integration.bash
cat >> ~/.bashrc <<'EOF'

# runex-init
[ -r "$HOME/.cache/runex/integration.bash" ] && . "$HOME/.cache/runex/integration.bash"
EOF
```

`runex export` も `runex init` と同じく、実行中のバイナリの絶対パスを埋め込みます。runex の置き場所が異なるマシン間で同じ rc ファイルを使うなら、`--bin runex` を付けてください。キー押下ごとに `PATH` から runex を探す形になります。

`runex doctor` は `# runex-init` のマーカーとキャッシュのヘッダーを確認します。マーカーが無い rc ファイルは "marker missing" と報告されます。0.1.16 より前の `eval "$(runex export bash)"` が残っている rc ファイルは outdated と報告されます。この形でも動きますが、シェル起動のたびに `runex export` が走り、キャッシュは使われません。

## シェルごとの注意点

### bash

bash 4.0 以降が必要です。macOS 付属の bash は 3.2 なので、Homebrew で新しい bash を入れてください（`brew install bash`）。

```bash
runex init bash
```

### zsh

```zsh
runex init zsh
```

### PowerShell

```powershell
runex init pwsh
```

貼り付けたテキストは、途中で展開されずにそのまま入ります。連携スクリプトは PSReadLine のキー待ち行列を見て、貼り付けと手入力を区別します。

**PSReadLine が読み込まれている必要があります。** 連携スクリプトは `Set-PSReadLineKeyHandler` でキーハンドラを登録します。PowerShell 7 と Windows PowerShell 5.1 はどちらも PSReadLine を同梱しており、連携スクリプトは両者を同じに扱います。`Get-Module PSReadLine | Format-List Name,Version,Path` で、読み込み済みかどうかと読み込み元を確認できます。

**プロファイルの場所は PowerShell 7 と 5.1 で異なります。** `runex init pwsh` が追記するのは PowerShell 7 のプロファイル `Documents\PowerShell\Microsoft.PowerShell_profile.ps1` です。Windows PowerShell 5.1 は `Documents\WindowsPowerShell\Microsoft.PowerShell_profile.ps1` を読みます。5.1 でも使うなら、7 のプロファイルにある 2 行のブロックを 5.1 のプロファイルに写してください。

**Windows PowerShell 5.1 では、dot-source を許す実行ポリシーが必要です。** 既定の `Restricted` は `.ps1` のキャッシュファイルを拒否するので、プロファイルの行が何もしません。次のコマンドで許可します。

```powershell
Set-ExecutionPolicy -Scope CurrentUser RemoteSigned
```

`AllSigned` の環境で `Documents\PowerShell\Modules` にある新しい PSReadLine が読み込まれると、起動のたびに「信頼されていない発行元のソフトウェアを実行しますか」と聞かれます。一度 `[A] Always run` を選ぶか、そのディレクトリを `$env:PSModulePath` から外して同梱の PSReadLine を読み込ませてください。

**Windows PowerShell 5.1 は、フックに渡すバッファから `"` を落とします。** ネイティブコマンドへの引数渡しで二重引用符が剥がれるためです。`"` を含む行は、展開時に `"` を失った形に書き換わることがあります。PowerShell 7 にはこの制限はありません。

### Nushell

```nu
runex init nu
```

source 行は `env.nu` に入ります。`runex doctor` がマーカーを探すのも `env.nu` です。

### cmd（Clink）

```cmd
runex init clink
```

clink のスクリプトディレクトリに `runex.lua` を書きます。現在の出力と異なるファイルが既にあるときは、上書き前に確認を求めます。実行後は新しい cmd ウィンドウを開いてください。

clink から runex への経路は cmd.exe のコマンドラインだけです。cmd.exe の引数には `"`、`%`、`!` を安全に含められないため、lua ファイルはバッファを 16 進数に変換して渡します。cmd.exe が `cmd /c` の後ろに受け付けるのは最大 8158 文字です（Windows 11 で計測）。このため、およそ 3900 バイトを超えるバッファは展開されず、トリガーキーは通常のスペースを入れます。経緯は [ADR 0003](decisions/0003-clink-hex-line-transport.md)（英語）に記録しています。

## `runex doctor` で確認する

`runex doctor` は設定の検証、`when_command_exists` に書いたコマンドの解決、各シェルの連携状態を 1 回でまとめて確認します。

```
$ runex doctor
[OK]   config_file: found: ~/.config/runex/config.toml
[OK]   config_parse: config loaded successfully
[OK]   integration:bash: marker found in ~/.bashrc
[OK]   integration:zsh: rcfile not found at ~/.zshrc — assuming this shell is not in use
[WARN] integration:pwsh: marker missing in ~/.config/powershell/Microsoft.PowerShell_profile.ps1 — run `runex init pwsh`
[OK]   integration:nu: rcfile not found at ~/.config/nushell/env.nu — assuming this shell is not in use
[OK]   integration:bash:cache: cache up-to-date at ~/.cache/runex/integration.bash
[OK]   integration:zsh:cache: no cache at ~/.cache/runex/integration.zsh — run `runex init zsh` to install
[OK]   integration:pwsh:cache: no cache at ~/.cache/runex/integration.ps1 — run `runex init pwsh` to install
[OK]   integration:nu:cache: no cache at ~/.cache/runex/integration.nu — run `runex init nu` to install
[OK]   command:lsd: 'lsd' found (required by 'ls')
```

セットアップに関係する行は次のとおりです。

| 行 | 意味 |
|---|---|
| `integration:<shell>` | rc ファイルに `# runex-init` のマーカーとキャッシュの source 行があるか。rc ファイルが無ければ「そのシェルは使っていない」とみなす。マーカーはあるが古い `runex export` 行が残っていれば WARN になり、直し方が本文に出る |
| `integration:<shell>:cache` | キャッシュファイルがあるか、ヘッダーのバージョンが現在のものか、記録されたバイナリがまだ存在するか |
| `integration:clink` | ディスク上の `runex.lua` が、このバイナリの出力と一致するか。runex を更新すると一致しなくなる |
| `effective_search_path`（Windows のみ） | `when_command_exists` の解決に使う PATH。`+user` と `+system` は、継承した PATH が不完全だったときにレジストリから補った件数。clink が起動した cmd セッションで起きる |

WARN の行には、直すためのコマンドが必ず書かれています。`runex doctor` 自身はファイルを編集しません。

## トラブルシューティング

トリガーキーを押しても展開されず、スペースが入るだけのときは次の順で確認します。

1. `runex doctor` を実行する。WARN の行に直し方が書いてある。
2. **`runex hook` が `unrecognized subcommand` で失敗する。** `PATH` の先にある別の `runex` が、連携スクリプトより古い。`which runex` と `runex version` でどのバイナリが応答したかを確認し、古い方を削除または更新する。連携スクリプトはフックが失敗すると通常のスペースを入れるので、キー束縛の不具合に見える。
3. **runex を更新したら clink で展開されなくなった。** `runex.lua` は自動では更新されない。`runex init clink` を実行し、新しい cmd ウィンドウを開く。`runex doctor` では `integration:clink: outdated` と表示される。
4. **clink で `lsd` を入れているのに `command:lsd not found` と出る。** clink が起動した cmd セッションは、不完全な PATH を継承することがある。runex はレジストリのユーザーとシステムの `Environment\Path` を補うので、どちらにも無いディレクトリはいずれかに追加する。
5. **pwsh で marker found と出るのに Space が効かない。** 順に、PSReadLine が読み込まれていない（`Get-Module PSReadLine` が何も出さない）、5.1 の実行ポリシーが `Restricted`、`AllSigned` が新しい PSReadLine を拒否している、のいずれか。対処のコマンドは [PowerShell の節](#powershell) にある。
6. **pwsh で `__runex_queued_key_count` が認識されない。** キャッシュファイルにヘッダーが 2 つある。`runex export pwsh` の出力に別のヘッダーを連結したときに起きる。対話ガードが関数定義を読み飛ばすので、`runex init pwsh` でキャッシュを書き直す。
7. **手で追加したルールが効かない。** `[[abbr]]` の編集は次のキー押下から効く。`[keybind]` の編集には `runex config reload` と新しいシェルが必要。
